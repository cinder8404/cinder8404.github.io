深度解析本周唯一长文

11月6日那组同步对照出来后，有一个结论值得单独写：在 chapel 测试网上，把快照解压到 HDD 并不会「慢一点」，而是会让整机进入一种看似正常、实际长期停滞的状态。这句话可以被反驳，反驳方式也简单——拿一台 SATA SSD 的机器跑同样流程，若同样时间内追平，那结论就要收窄为「机械盘不适用」。

判断：HDD 组在第 31 小时仍落后尖峰 1,240,000 块，而 NVMe 组已在第 9 小时 40 分完成 state 校验。两者的差距不在网络带宽——两组下行都稳定在 42Mbps 左右——而在 LevelDB 的随机写放大。

一、时间线：两台机器都做了什么

  • 10月31日 21:10，两台机器下载同一份 chapel 快照，压缩包 46.2GB，MD5 一致。
  • 10月31日 22:05，NVMe 组解压完毕并启动 geth --syncmode snap；HDD 组 23:40 才解压完成。
  • 11月1日 07:50，NVMe 组 eth_syncing 返回 false，块高与浏览器一致。
  • 11月1日 23:10，HDD 组块高 41,002,880，浏览器当时 42,242,910，仍差约 124 万块。
  • 11月2日 09:00，HDD 组日志出现 Write stall，磁盘 await 均值 380ms。

三、说法差异：社区里两种相反的抱怨

10月28日 BSC 开发者论坛一个帖子里，有人称「机械盘也能跑，主要是内存要 32GB」。同日另一条回复则说「16GB 内存 + HDD 三天都没同步完」。这两句并不完全冲突：前者可能用的是 snap 同步且只等首块，后者大概率是 full 同步在重放旧块。差别落在 --syncmode 参数，而不是硬件本身。转述到这里为止，谁对谁错需要各自贴出启动命令。

四、规则前后变化：Geth 1.4.12 的日志差异

版本从 1.4.9 升到 1.4.12 后，debug_traceCall 默认不再展开内部调用层级，需要显式加 --tracer 参数；同时 Write stall 的日志措辞从 database compaction too slow 变成 Write stall detected。如果按旧日志关键字写监控告警，升级后会静默失效——这一点在 11月7日的修订里补进了正文。

五、推测与边界

把上面数据外推到主网要谨慎：主网 state 规模约为 chapel 的四十余倍，HDD 的随机写劣势只会更明显，但具体倍数没有实测，不写具体数字。另一个未验证项是不同内核 IO 调度器（mq-deadline 与 none）对结果的影响，11月9日会补一组对照。

体验指南从零到能查一笔交易

装好客户端并确认版本

Geth 1.4.12 起 geth version 输出里带 commit hash，先记下来。不同小版本的快照格式不通用，混用会在解压后报 state root mismatch。

下载 chapel 快照并校验 MD5

46.2GB 的包，校验值在发布页可见。跳过校验直接解压，出问题后无法判断是包损坏还是配置错误，会白耗一晚上。

启动时固定 syncmode 与缓存

--syncmode snap --cache 4096 是这轮实验用的参数。缓存低于 2048 时，HDD 组的 Write stall 出现时间提前约 3 小时。

用区块高度而不是「已连接」判断完成

eth_syncing 返回 false 只是本机状态，必须与 BscScan 上 chapel 的当前高度对比。11月1日那次就是靠对比才发现 HDD 组落后。

拿一笔真实交易练查证

选一笔 BEP-20 转账，依次看 tx 页签、internal tx 页签、logs 页签，确认金额、手续费与事件三者对得上，再去看失败交易长什么样。

常见问题

chapel 测试网快照解压后块高落后一百多万，该怎么补？
先看 eth_syncing 返回的对象里 currentBlock 与 highestBlock 的差值。若差值在缩小，说明 snap 同步在正常追块，继续等；若两小时不动，检查日志有无 Write stall 或 peer 数为 0。11月1日 HDD 组就是 Write stall 导致假性停滞。
BscScan 上显示成功，为什么钱包提示交易失败？
钱包看的是本地广播后返回的 receipt 状态，而 BscScan 展示的是链上最终结果。常见于 RPC 返回了旧高度缓存。换一个 RPC 端点重新查询同一 tx hash，若结果不一致，以浏览器为准。
eth_estimateGas 的结果为什么总是比实际扣费高？
估算值按当前状态模拟，未计入后续区块基准费变化；合约里若有余额判断，模拟时条件成立而实际执行时余额已被前一笔交易消耗，也会造成偏差。11月4日那篇列了四种来源，逐条对过再提交。
公共 RPC 抓 eth_getLogs 老是被限流，有替代方案吗？
把查询区间缩到 500 块以内，或改用付费归档端点。bsc-dataseed 系列对区间宽度和调用频率都有约束，历史事件量大时逐段续抓，记录最后成功的块高作断点。
转账 BEP-20 代币，Gas 设 21000 为什么直接失败？
21000 只够纯 BNB 转账。代币转账要走合约，常见消耗在 51000 上下，approve 类操作起点约 46000。用 eth_estimateGas 拿到值后乘 1.1 提交，别写死。
